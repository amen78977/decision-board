# تحويل Decision Board إلى منتج قابل للدخل

## الخلاصة التنفيذية

Decision Board اليوم **نواة تقنية مفتوحة المصدر** وليست منتج SaaS مدفوعًا. قوته الحقيقية ليست «ستة وكلاء»، بل بروتوكول يفرض عزلًا متناظرًا، وفحصًا للوقائع، وادعاءات قابلة للإبطال، وثقة رقمية يمكن مراجعتها لاحقًا. هذه النواة مناسبة جدًا لبناء قناة اكتساب مجانية، لكنها لا تكفي وحدها لفرض اشتراك؛ فالمستخدم يستطيع تثبيتها ونسخها دون حساب أو خدمة مركزية.

المسار الموصى به هو **open-core**: تبقى النواة المحلية مجانية وشفافة، بينما تُباع طبقة خدمة اختيارية توفر ما يصعب بناؤه محليًا: مزامنة الدفتر، تذكيرات النتائج، لوحة معايرة، مساحات عمل للفرق، قوالب قرارات متخصصة، تقارير قابلة للتصدير، وسياسات خصوصية وأمان للمؤسسات. لا ينبغي تحويل العزل أو البروتوكول الأساسي إلى paywall؛ فهما مصدر الثقة والانتشار.

## التموضع المقترح

بدل تسويق المنتج على أنه مستشار لكل قرار شخصي أو مالي أو صحي، ابدأ بشريحة لها مشكلة متكررة واستعداد أعلى للدفع: **المؤسسون ومديرو المنتجات والهندسة الذين يتخذون قرارات عالية الأثر تحت عدم اليقين**. أمثلة الاستخدام هي إطلاق منتج، تغيير استراتيجية التسعير، التوظيف الأول، اختيار بنية تقنية، أو قرار تمويل. هذا التموضع يحافظ على جوهر المشروع ويقلل مخاطر تقديم نصائح شخصية حساسة، كما يجعل قيمة سجل القرار قابلة للقياس داخل فريق.

> الوعد التسويقي المقترح: **«قبل أن تلتزم بقرار مكلف، اجعل نظامك الذكي يبني أقوى حجة ضده — من دون أن يرى صياغتك المنحازة.»**

| العنصر | الصياغة المقترحة |
|---|---|
| العميل الأول | مؤسس أو مدير منتج/هندسة في فريق صغير |
| المشكلة | قرارات مكلفة تُتخذ من خلال نقاشات تميل إلى تأكيد الرأي الأصلي |
| النتيجة المباعة | قرار موثق، افتراضات واضحة، اعتراض قابل للاختبار، وثقة قابلة للمراجعة |
| قناة الاكتساب | إضافة Claude Code مجانية، أمثلة تشغيل حقيقية، تقارير ميدان، ومحتوى عن تحيز الذكاء الاصطناعي |
| سبب الدفع | استمرار الذاكرة، معايرة النتائج، العمل الجماعي، التصدير، والحوكمة |
| ما لا نعد به | صحة القرار، إزالة المخاطرة، أو تقديم مشورة قانونية/طبية/مالية مهنية |

## طبقات العرض

| الطبقة | ما يحصل عليه المستخدم | الهدف التجاري |
|---|---|---|
| **Free / Local** | البلَغن الكامل، التشغيل المحلي، الدفتر المحلي، بلا telemetry أو network calls من المشروع | اكتساب وثقة وتوزيع واسع |
| **Pro / Individual** | مزامنة اختيارية، سجل نتائج وتذكيرات، لوحة معايرة، قوالب، تصدير Markdown/PDF، واختيار مزود النموذج | اشتراك فردي منخفض الاحتكاك |
| **Team** | مساحة فريق، قوالب مشتركة، أدوار وصلاحيات، سجل تدقيق، تقارير قرارات، وفوترة مركزية | رفع قيمة الحساب وتقليل التسرب |
| **Assisted rollout** | تهيئة خاصة، قوالب حسب المجال، نشر محلي أو خاص، وتدريب الفريق | إيراد خدمات مبكر قبل اكتمال SaaS |

الأسعار التالية **فرضيات اختبار وليست توقعًا للدخل**: يمكن بدء مقابلات البيع بنطاق 9–15 دولارًا شهريًا للفرد، و29–49 دولارًا شهريًا للفريق الصغير، ثم تعديلها بعد ملاحظة الاستخدام والاستعداد الفعلي للدفع. وجود تطبيق منافس منخفض السعر لا يعني أن السعر المنخفض هو الميزة؛ ذلك المنتج يبيع سرعة اتخاذ قرار بسيط، بينما هذه المنظومة يجب أن تبيع تقليل تكلفة قرار متكرر وعالي الأثر.[1]

## ما يجب أن يبقى مجانيًا وما يمكن بيعه

لا تبع «الصدق» أو «المعارض» أو القواعد الأساسية؛ بيعُها سيضعف الانتشار ويشجع المستخدم على إزالة الحواجز. أصبح في النواة المجانية أمر `/review` يفتح حلقة التعلم الأساسية: مراجعة القرارات المستحقة وتحديث المعايرة من النتائج. ما يمكن بيعه فوق ذلك هو **الاستمرارية والحوكمة على نطاق أكبر**: مزامنة اختيارية، الاحتفاظ بنتائج القرارات، مقارنة الثقة بالنتيجة بعد أسابيع أو أشهر، مشاركة قرار مع فريق، ربط الأدلة بمصدر، وتطبيق سياسات المؤسسة مع بقاء البيانات تحت سيطرة العميل.

ويجب أن يكون جمع البيانات اختياريًا وصريحًا. الوضع المجاني المحلي لا يرسل نصوص المستخدم إلى خادم المنتج، والنسخة السحابية لا تحفظ النص الكامل افتراضيًا إلا بموافقة واضحة. يمكن حفظ ملخص مهيكل أو hash للقرار عند الحاجة إلى المعايرة، مع زر حذف وتصدير كاملين.

## مبدأ التنفيذ

لا يُنصح بإضافة بوابة دفع أو استدعاءات شبكة إلى البلَغن الحالي مباشرةً. الإضافة الموزعة يجب أن تظل قابلة للفحص والعمل دون حساب؛ أما المنتج المدفوع فيُبنى كخدمة منفصلة تتصل عبر MCP أو واجهة ويب، وتقدم الحسابات والفوترة والمزامنة. بهذه الطريقة لا تتحول الإضافة إلى آلية اشتراك هشة ولا تُفسد وعد «لا telemetry».

المسار التقني المقترح هو:

```text
Claude Code plugin (مجاني، local-first)
              │
              ├── تشغيل محلي كامل بلا حساب
              │
              └── Pro bridge اختياري عبر MCP/HTTPS
                         │
                  Auth + billing + workspace
                         │
             Journal sync + calibration + exports
```

## مؤشرات النجاح

يجب قياس القمع السلوكي بدل الاكتفاء بعدد النجوم أو التنزيلات. المؤشر الأول هو نسبة من يثبت الإضافة ويشغل أول قرار حقيقي. ثم نسبة من يكمل ردًا من المستوى 2 أو 3، ونسبة من يسجل قرارًا فعليًا، ونسبة من يعود لمراجعة نتيجة، وأخيرًا نسبة من يطلب تجربة Pro أو يدفع. في الوضع المجاني تكون القياسات محلية أو اختيارية؛ لا تضف telemetry صامتة إلى النواة.

| المرحلة | المؤشر | سؤال القرار |
|---|---|---|
| الاكتشاف | تثبيت الإضافة أو نسخ CHAT.md | هل الرسالة واضحة؟ |
| التفعيل | أول تشغيل قرار حقيقي | هل يصل المستخدم للقيمة بسرعة؟ |
| القيمة | قرار محفوظ + خطوة تحقق ملموسة | هل الناتج قابل للتنفيذ؟ |
| الاحتفاظ | مراجعة نتيجة بعد 30–90 يومًا | هل الدفتر عادة متكررة؟ |
| الإيراد | تجربة Pro ثم اشتراك أو عقد فريق | هل المزايا المدفوعة تحل ألمًا حقيقيًا؟ |

## خطة 90 يومًا

### الأيام 1–30: إثبات المشكلة

ثبّت النواة الحالية، أصلح مشكلات التثبيت، وانشر الديمو الحقيقي كما هو. نفّذ 10–15 مقابلة مع مؤسسين أو مديري منتجات، واطلب منهم تشغيل قرارات حقيقية بدل سؤالهم إن كانوا «يحبون الفكرة». الهدف هو اكتشاف قرار متكرر له تكلفة واضحة، لا جمع مجاملات.

### الأيام 31–60: اختبار الخدمة يدويًا

أنشئ نسخة Concierge بسيطة: يستعمل العميل البلَغن المحلي، ثم يرفع قرارًا مهيكلًا بموافقته إلى مساحة خاصة، ويحصل على تذكير مراجعة وتقرير معايرة يدوي. إذا لم يدفع ثلاثة عملاء تجريبيين مبلغًا صغيرًا مقابل هذه الخدمة، فلا تبنِ SaaS كاملًا بعد؛ غيّر الشريحة أو الميزة.

### الأيام 61–90: بناء أصغر Pro قابل للدفع

ابنِ حسابًا واحدًا، مساحة عمل صغيرة، دفترًا متزامنًا، تذكير نتيجة، وتصديرًا واضحًا. أجّل التكاملات الكثيرة والخصائص الاجتماعية. اختبر الدفع مع عميلين أو ثلاثة، واجعل كل قرار سحابي قابلًا للحذف والتصدير، وسجّل أسباب الانسحاب لا عدد المستخدمين فقط.

## قنوات التوزيع

يوجد مسار رسمي لتوزيع الإضافات عبر أسواق Claude: السوق يوفر الاكتشاف وتتبع الإصدارات والتحديثات، ويمكن تقديم الإضافة إلى دليل Claude للمراجعة.[2] لذلك يجب تحسين metadata، وREADME، والديمو، واختبارات التثبيت قبل طلب الإدراج. القبول في الدليل ليس مضمونًا، لكنه قناة اكتساب مناسبة للنواة المجانية.

القناة الثانية هي تقارير الميدان: كل خطأ حقيقي في الكاشف أو في سلوك الطاولة يتحول إلى حالة اختبار ومقال قصير يشرح المشكلة والإصلاح. هذه القناة أكثر مصداقية من ادعاء أن النظام «لا يخطئ»، وتتماشى مع فلسفة المشروع التي تسجل الفشل بدل إخفائه.

## قرارات لا ينبغي اتخاذها الآن

لا تبنِ تطبيقًا عامًا لاتخاذ كل قرارات الحياة قبل إثبات شريحة واحدة. لا تضف إعلانات أو telemetry خفية. لا تدّعِ أن ستة وكلاء تعني ستة عقول مستقلة. لا تستخدم أرقام نجاح أو دقة بلا مصدر. ولا تُضعف العزل أو فحص الوقائع لتقليل الكلفة قبل أن تقيس قيمة النتيجة؛ الأفضل هو بوابة العمق الحالية أو اختيار نماذج أرخص مع اختبار عدم تراجع السلوك.
